So the formula is: usable hosts equals two to the power of the host bits, minus two. And the minus two is because one address is the network address and one is the broadcast address, and neither can be given to a machine.

Next, what happens when you type a URL and press enter. This is a story you recite in order.

The browser checks its cache. Then DNS turns the domain name into an IP address, because you can't connect to a name, only to an address. Then a TCP connection opens, that's the three way handshake. Then TLS negotiates if it's HTTPS. Then the browser sends an HTTP GET request. That usually hits a reverse proxy, something like Nginx or Caddy, before it reaches the application server. The server responds with HTML and a status code. The browser parses that HTML into a DOM, discovers it also needs CSS, JavaScript and images, and fetches those. Then it renders the page and runs the JavaScript.

TCP versus UDP, quickly. TCP is connection based, ordered and reliable. It acknowledges and retransmits. That's web and email. UDP just fires packets with no guarantee. That's video calls, games and DNS, where a late packet is worse than a lost one.

Now REST. And this is your home ground, so this is quick.

REST treats everything as a resource with an address, and the HTTP verb says what you want done to it.

GET reads and changes nothing. POST creates. PUT replaces the whole thing. PATCH updates part of it. DELETE removes.

Two words they may ask about. Safe means no side effects, and GET is safe. Idempotent means doing it twice has the same effect as doing it once. GET, PUT and DELETE are idempotent. POST is not, because two POSTs make two records.

And that's exactly why webhook handlers need an idempotency key. You already do this in production, with a unique event id on the webhook table so a replayed webhook can't double charge anybody. If they ask about idempotency, that's your answer, and it's a real one.

Now. JavaScript. Sit up for this part.

You're a Python developer, and the danger is that you'll answer JavaScript questions using Python reasoning. So deliberately switch languages in your head when you see one.

The most asked JavaScript question in existence is double equals versus triple equals.

Double equals converts the types before comparing. So the string five, in quotes, double equals the number five, is true.

Triple equals compares value and type. So the string five triple equals the number five is false.

Always use triple equals. And know one more pair: null double equals undefined is true, but null triple equals undefined is false.

Var, let and const. Var is function scoped. It leaks out of if blocks and for loops to the whole function. Let and const are block scoped, they stay inside the curly braces.

Hoisting. Declarations get moved to the top of their scope before the code runs. With var, the variable exists but holds undefined, so printing it before its line gives you undefined, not an error. With let and const, it exists but throws if you touch it early. That gap is called the temporal dead zone.

And const stops reassignment, not mutation. You can still push into a const array. Reassigning the whole array would throw.

Now the event loop, which is the hardest JavaScript question you're likely to get.

JavaScript runs one thing at a time. Slow work like network calls and timers gets handed off, and the callback gets queued to run later. That's how single threaded code stays responsive. It's the same idea as async and await in FastAPI, which you already understand.

But there are two queues, and they don't have equal priority. Promises go on the microtask queue. Timers, like setTimeout, go on the macrotask queue. And microtasks always run first.

So if you see code that logs one, then sets a timeout logging two with zero delay, then a resolved promise logging three, then logs four, the output is one, four, three, two. Synchronous first, so one and four. Then the promise, three. Then the timer, two. Even with zero milliseconds, the timer goes last. That surprises people, and that's why they ask it.

Closures. A closure is a function that keeps access to the variables from the scope where it was defined, even after that scope has finished. It's how JavaScript does private state. A counter function that remembers its count between calls, without exposing it.

Null versus undefined. Undefined means no value was ever assigned. Null means somebody deliberately set it to nothing. And one oddity worth knowing, typeof null returns the string object, which is a long standing bug in the language.

Events. Things that happen in the browser. Click, submit, keypress. Bubbling means the event fires on the target element first, then travels up through each parent. Stop propagation halts it. Bubbling is what makes event delegation work, one listener on a parent handling clicks on many children.

And two quick ones. Map returns a new array with each item transformed, it does not change the original. Filter selects. Reduce collapses to a single value. Same mental model as a Python list comprehension. And an async function always returns a promise, even if you return a plain number.
