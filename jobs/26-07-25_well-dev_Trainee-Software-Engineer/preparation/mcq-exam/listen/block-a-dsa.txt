BLOCK A. DATA STRUCTURES AND ALGORITHMS.

Okay. This is the biggest part of the WellDev paper, so this is the block that pays best. Listen once, all the way through, before you read anything. You don't need to take notes. Just follow it.

First, time complexity. Big O.

Big O is a way of saying how much slower a program gets when the data gets bigger. You do not calculate it with maths. You count loops.

No loop at all, just jumping straight to something, that's constant time. Order one.

One loop over the data, that's linear. Order n.

A loop inside another loop, that's quadratic. Order n squared. Remember this: nesting multiplies, but putting two loops side by side only adds. Two separate loops over the same list is still order n, not n squared. People get that wrong.

Cutting the problem in half every step, like binary search, that's logarithmic. Order log n.

And good sorting sits in between, at n log n.

The one they love to ask is recursive Fibonacci. What's the complexity? It's order two to the power n. Exponential. The reason is that every call makes two more calls, so the tree of calls doubles at every level. And the fix, if they ask, is memoisation. You cache each result the first time you work it out, and that brings it down to order n. Or you just use a loop with two variables, which is order n time and constant space.

Now here's a trap worth hearing twice. Time and space are different questions. If they ask for space complexity, they're asking how much extra memory you use, not how long it takes. And recursion is not free on memory. A recursive function that adds up one to n uses order n space, because n calls are stacked up waiting for each other. The loop version does the same job in constant space. Read the word. Time, or space.

Next, sorting.

You do not need to write these. You need to know their names and their speeds.

Three slow ones. Bubble sort, selection sort, insertion sort. All order n squared.

Three fast ones. Merge sort, quick sort, heap sort. All order n log n on average.

Here's the question they actually ask. Which sorting algorithm is n log n in the worst case? The answer is merge sort, or heap sort. Not quicksort. Quicksort averages n log n but it degrades to n squared if you keep picking a bad pivot, and the classic bad case is already sorted data with a first element pivot.

So then the follow up is, if quicksort has a worse worst case, why does everybody use it? Two reasons. It sorts in place, so it needs almost no extra memory, while merge sort needs order n extra. And its constant factors are smaller, so in the real world it's just faster. You fix the bad pivot by choosing randomly, or by median of three.

One more thing on sorting. Stability. A stable sort keeps two equal items in their original order relative to each other. Merge sort is stable. Insertion and bubble are stable. Quicksort and heap sort are not. That matters when you sort by one field and want the previous ordering preserved underneath.

And one small gift of a question. What's the best case of insertion sort? It's order n, on data that's already sorted. It's the only slow sort with a genuinely good best case.

Now, arrays and linked lists.

An array is one solid block of memory. All the items sit side by side, so the computer can jump straight to item five hundred by doing arithmetic on the address. That's constant time.

A linked list is scattered. Each item holds a value and the address of the next item. To reach item five hundred you have to walk through four hundred and ninety nine of them first. That's linear time.

But flip it around. Inserting at the front of an array means shifting every single element along. Inserting into a linked list means changing one pointer. So arrays win on lookup, linked lists win on insertion and deletion.

Three questions come from this, and they've all been asked at WellDev.

One. In C, if you print the array name on its own, what do you get? You get the base address. The memory address of the first element. The array name decays into a pointer to element zero.

Two. Can you do binary search on a sorted linked list? Technically yes, practically no. Binary search needs to jump to the middle in constant time, and a linked list can't jump. Getting to the middle costs you order n, so you've lost the entire benefit.

Three. Reverse a linked list. Three pointers. Previous, current, next. You walk along and flip each arrow backwards. The trap is that you must save the next pointer before you overwrite it, or you lose the rest of the list.

Now stacks and queues.

A stack is last in, first out. Like a pile of plates. You add and remove from the same end.

A queue is first in, first out. Like a line at a shop. In at the back, out at the front.

That's genuinely all they are. The questions come from tracing.

Here's the one WellDev question we know is real. Items A, B, C, D and E are pushed onto an empty stack in that order. Then things get popped. And the answer is always found by writing the letters down and crossing them off. Do not do it in your head. Eight seconds of writing removes all the risk.

Two puzzles from this area.

Delete the middle element of a stack without using another data structure. The answer is recursion. You pop items off one at a time, and the call stack holds them for you. When you reach the middle you drop it, then you push everything back as the recursion unwinds. And the reason that's allowed is that the call stack isn't a data structure you declared. If you say it's impossible, you've failed the question they were actually asking.

Build a stack using two queues. The point is that one of the two operations has to become expensive, and you choose which. A queue only gives you its oldest item, but a stack needs its newest, so somewhere you have to reverse the order, and reversing costs a pass over everything.

And memorise this pair, because it comes up constantly. DFS uses a stack. BFS uses a queue.

Now trees.

A binary search tree keeps everything smaller on the left and everything bigger on the right. That rule is what makes searching fast, because at every step you throw away half the tree.

Three traversals. The name tells you when you visit the node itself. Pre order, node first. In order, node in the middle. Post order, node last.

And the one to remember is that in order traversal of a binary search tree comes out sorted, always. If they ask for descending order, you do reverse in order. Right, node, left.

Searching a binary search tree is order log n, but only when it's balanced. If you insert already sorted data it turns into a straight line, which is just a linked list, and search becomes linear. Say that caveat out loud when you answer. That's exactly what they're listening for.

Now graphs.

A graph is dots joined by lines. Cities and roads.

DFS goes deep down one path before backing up. It uses a stack, or recursion. BFS spreads out level by level. It uses a queue.

And here's why that matters. BFS finds the shortest path in an unweighted graph, because it explores in rings of increasing distance, so the first time you touch the target you got there the shortest way. That's why the knight on a chessboard question, minimum number of moves, is a BFS problem. Every knight move costs the same, so it's an unweighted graph.

Minimum spanning tree. That's the cheapest set of connections that still joins everything together with no loops. Two algorithms build one. Kruskal, which sorts all the edges and keeps adding the cheapest one that doesn't make a cycle. And Prim, which grows outward from one node, always taking the cheapest edge to somewhere new. Both are greedy.

Greedy means you take the best looking option right now and you never go back and reconsider. For minimum spanning trees, greedy happens to give the genuinely correct answer. But it doesn't always. If they ask whether greedy works for some other problem, the honest answer is that it depends on whether the problem has the greedy choice property, and often it doesn't.

Two ways to store a graph. An adjacency list, which is each node plus a list of its neighbours, and that's efficient when there aren't many edges. Or an adjacency matrix, which is a full grid, fast for asking are these two connected, but it uses space proportional to the number of nodes squared.

Last thing. Recursion.

Every recursive function needs two parts. A base case that stops it, and a recursive case that makes the problem smaller. Miss the base case and it runs forever.

Think of it as delegation. I don't know the answer for five, but if somebody hands me the answer for four, I can finish it. And eventually somebody gets a problem so small they just know it.

Every waiting call sits on the call stack. That's why deep recursion overflows, and that's why the call stack can be borrowed as free temporary storage, which is the trick behind the stack middle deletion puzzle.

Right. Three things to carry out of this block.

One. Nesting multiplies, sequencing adds. And naive recursive Fibonacci is two to the n, fixed by memoisation.

Two. Merge and heap sort are n log n in the worst case. Quicksort is not, but it's still faster in practice because it sorts in place.

Three. DFS uses a stack, BFS uses a queue, and BFS is the one that gives you shortest path.
